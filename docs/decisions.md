# Decisions log

Where the brief was ambiguous, we picked the option that makes the product more honest and the demo more reliable. Newest last.

| # | Decision | Why |
|---|----------|-----|
| 1 | **Fusion keeps the brief's structure but is calibrated**: `score = 100 × max(rule_hit, Σ wᵢ·signalᵢ)`, with the weighted sum mapped piecewise-linearly so the tuned thresholds land on the fixed UI bands (t_yellow → 40, t_red → 75). | With the literal weights (0.4/0.2/0.2/0.2), one engine alone can never pass 40, so a certain duplicate could only ever be yellow. The mapping is monotone, so ranking metrics are unchanged and the 40/75 bands stay stable for users. |
| 2 | **Weights and thresholds are tuned on two out-of-time folds** (train 1-6 → tune 7-8, train 1-8 → tune 9-10), maximising recall subject to false alarms ≤ 4% and red false alarms ≤ 0.5%. We also add one design rule: a duplicate or graph signal of 0.9 must reach red on its own. | A single 2-month fold overfit (validation FAR 3.9% became 8.4% on test). Two folds give ~1,600 tuning payments. The rule encodes the product promise "a near-certain duplicate or an undisclosed employee link is enough to block". The prompt's default weights are evaluated too, as an ablation (`fusion_prompt_defaults_validation` in metrics.json). |
| 3 | **The XGBoost risk model sees behaviour features only.** Duplicate and graph signals are separate engines, not XGBoost inputs. | Every engine's contribution stays separately explainable in the UI (engine bars), and the ablation table can show what each engine adds. |
| 4 | **"Creator = approver" is modelled as `creator_can_approve`** (the creator holds an approval role), plus a hard workflow control: the creator of a yellow line gets 403 when trying to approve it. | At scoring time (before release) the approver is unknown. Using the realised approver would leak the future into training. |
| 5 | **Duplicate candidates are invoices received before this invoice was received**, not before the payment. | Otherwise the original invoice's own payment would be flagged as a duplicate of the copy that arrived later. |
| 6 | **"Days since invoice date" replaced "time from invoice entry to payment".** | Uploads are scored the moment they arrive, so system-entry timing made every upload look rushed. The document date carries the same fraud signal (fake invoices are paid a day after they are dated) without penalising the upload workflow. |
| 7 | **Training labels come only from resolved cases.** The generator records the months 1-10 frauds as confirmed historical audit cases; months 11-12 have no cases. `labels.csv` is read only by `ml/evaluate.py` and the tests. | The app never sees ground truth, and the same label path powers `/admin/retrain`. Unaudited payments are excluded from retraining (unknown labels), never treated as negatives. |
| 8 | **Synthetic-data realism added after first results looked too clean**: legit price revisions (4-12%), "stealth" fraud variants (forged bank letters processed by the usual clerk, registered shell vendors with tax and concrete items, weekday-evening self-approvals, splits further under the limit), and a disclosed related-party vendor. | The first model put a brittle split at a 1.05× unit-price ratio and blocked a legit vendor. Realistic noise moved the boundary and made the metrics believable. |
| 9 | **Related-party register**: a vendor in the register (disclosed under the Companies Act 2017) has its employee links multiplied by 0.2 (shown, but down-weighted). | A disclosed brother-in-law's transport company is a fact to show, not a fraud signal to fire on every weekly payment. |
| 10 | **Demo week opening cash is calibrated by the generator**: the largest opening balance at which releasing every line still breaches the reserve that week, and the smallest at which blocking the planted frauds keeps all 13 weeks above it (midpoint if both hold). | This is a scripted scenario on synthetic data, documented here and in `demo_calibration.json`. All model metrics come from the separate months 11-12 backtest, never from the demo week. |
| 11 | **13-week projection includes only invoices already issued or received** (no new sales/purchase forecast). Open payables are paid in the weekly run covering their due date. Utility bills after this month are assumptions. | Keeps every number traceable to a fact or a model estimate. The limitation is shown on the cash screen. |
| 12 | **Expected collection date**: due date + the customer's median past delay. Overdue beyond the median → the customer's 80th-percentile delay. Beyond that → as-of + 7 days, marked as an assumption. | A deterministic baseline as specified, never a past date, and it avoids piling every stale receivable into one week. |
| 13 | **Late-payment model selection happens on months 9-10 (validation), not on the test months.** XGBoost shipped because it beat logistic regression and the baseline on validation PR-AUC. Output is labelled "late-payment risk score" because the reliability check failed our strict calibration rule (max bin gap ≤ 0.12). | Selecting on the test set would bias the reported numbers. |
| 14 | **Bank file export is allowed when no line is pending.** Blocked, held and rejected lines are excluded, not "open". | Otherwise one open case would freeze the whole run; cases continue independently. |
| 15 | **A false alarm on a red line does not erase the score.** Resolving the case as a false alarm records an override (`override_decision = review`), audit-logged, so the line needs a second approver. | "Every score and every human decision is stored, never overwritten." |
| 16 | **Document reader confidence is deterministic**: agreement between Gemini and the PDF-text/regex reading, plus validators (sums, 18% tax, NTN, IBAN mod-97). It is not the LLM's self-reported confidence. | LLM self-confidence is unreliable; this keeps "deterministic code decides". |
| 17 | **Cached extractions** in `demo_week/extraction_cache/` are genuine outputs of our own pipeline (written by `ml.eval_extraction`), replayed only when no engine can read a file, and labelled "cached" in the UI. | Satisfies "final fallback: cached extraction for demo PDFs" without inventing results. |
| 18 | **shadcn/ui components are vendored by hand** (same Radix + CVA + tailwind-merge pattern). | The shadcn registry host was blocked by the build environment's network policy; npm was available. |
| 19 | **Next.js 16 Cache Components turned off.** | The app is client-rendered against an external FastAPI. Cache Components would require Suspense around every dynamic param for no benefit. |
| 20 | **CPU-only XGBoost (`xgboost-cpu`)**. | The default wheel pulls ~470 MB of NVIDIA NCCL; the CPU wheel is 6 MB and keeps the image small. |
| 21 | **One uvicorn worker.** Models and the scoring context are cached in process memory and invalidated by a data-version counter. | Stays under the 512 MB budget and keeps the cache coherent. |
| 22 | **Demo bank change is approved by nobody** (the fraud), while legit changes made in the app become `pending` until a different user approves them. | Shows the new control (second user for bank changes) alongside the historical weakness it fixes. |
